======================================================================
  DISCUSSÃO
======================================================================

  1. A VERSÃO PARALELA FOI MAIS RÁPIDA?
  ------------------------------------------------------------------
  Sim. O melhor cenário foi 20 workers: 22.614 s vs. 45.955 s sequencial.
  Speedup de 2.03x — redução de 50.8% no tempo total.

  Com 8 workers (oversubscription), o tempo foi 23.984 s — mais lento que o melhor paralelo,
  confirmando que criar mais processos do que núcleos físicos piora o desempenho.

  2. O TAMANHO DO CHUNK INFLUENCIOU?
  ------------------------------------------------------------------
  Sim, de duas formas interdependentes:

  • Chunks maiores (menos workers) → menos overhead de fork/join,
    mas sub-utilização dos núcleos disponíveis.
  • Chunks menores (mais workers)  → maior paralelismo, porém:
    - Mais processos competem pelo mesmo arquivo em disco (I/O contention).
    - Aumenta o custo de serialização/desserialização via pickle.
    - Em oversubscription, o SO realiza context-switch frequente,
      adicionando latência sem ganho real de CPU.

  Exemplo concreto (dentro da capacidade física):
    2 workers → chunk médio ≈ 891.8 MB   |   4 workers → chunk médio ≈ 445.9 MB

  3. HOUVE CUSTO EXTRA DE CRIAÇÃO DE PROCESSOS?
  ------------------------------------------------------------------
  Sim. Três fontes de overhead foram mensuráveis:

  a) Fork do SO: cada Pool(n) faz n chamadas fork(), que copiam
     o espaço de memória do processo pai (copy-on-write).
     Em Python 3.11/Linux o fork é rápido (~5–20 ms/processo),
     mas com 20 processos acumula ~100–400 ms antes de iniciar.

  b) Pickle (serialização): os argumentos (filepath, start, end)
     e o Stats retornado são serializados/desserializados em cada
     chamada a pool.map(). Para dados simples isso é desprezível,
     mas escala com o volume dos resultados parciais.

  c) Context-switch (oversubscription): com workers > núcleos,
     o kernel alterna processos no mesmo núcleo, adicionando
     latência de cache miss sem aumentar throughput de CPU.

  Overhead mensurado na oversubscription (relativo ao melhor):
     8 workers: +1.370 s acima do mínimo
    10 workers: +1.339 s acima do mínimo

  4. EM QUE CENÁRIO A PARALELIZAÇÃO COMPENSA?
  ------------------------------------------------------------------
  A paralelização com multiprocessing compensa quando:

  ✔ O processamento é CPU-bound (parse, cálculo, transformação)
    e o custo de computação por linha é alto o suficiente para
    amortizar o fork e a contenção de I/O.

  ✔ O arquivo está em storage de alta velocidade (SSD NVMe,
    RAM disk, object storage com leitura paralela) — elimina
    o principal gargalo observado neste experimento.

  ✔ Os blocos são independentes — sem necessidade de estado
    compartilhado ou locks entre workers (como neste script).

  ✔ O número de workers é ≤ núcleos físicos disponíveis.
    Nesta máquina: 4 núcleos → máximo útil = 4 workers.

  ✘ NÃO compensa quando:
    - O arquivo está em HDD/rede lenta (I/O-bound domina).
    - O dataset é pequeno (overhead > ganho).
    - O workers excede os núcleos (oversubscription).

  Para escalar além de uma única máquina:
    → Ray   — multiprocessing distribuído, mesma API Pool
    → Dask  — DataFrame com chunked CSV nativo e lazy eval
    → Spark — PySpark para clusters com shuffle distribuído
